## تحديث صلاحيات الفويد والمرتجع والكومنت — 2026-11-05

أزيل وصف `Deduct wasted stock` من شاشة الفويد، وأضيف كومنت مستقل إلى الفويد والمرتجع.
كومنت الفويد محفوظ في `POS Order Item Cancellation.comment`، وكومنت المرتجع في `POS Return.comment`.
يسجل كلاهما المستخدم المعتمد ورابط `Approval Challenge` عند اعتماد مدير.

الأربع صلاحيات في POS User مستقلة، وتُقرأ من قاعدة البيانات عند كل عملية:

| الحقل | الصلاحية |
| --- | --- |
| `can_void_items` | إلغاء الأصناف المؤكدة بدون اعتماد |
| `can_void_waste` | اعتبار الأصناف الملغاة هالكًا بدون اعتماد، بالإضافة إلى صلاحية الفويد |
| `can_request_returns` | المرتجع بدون اعتماد |
| `can_return_waste` | مرتجع هالك بدون اعتماد، بالإضافة إلى صلاحية المرتجع |

تعديل POS User يرسل تحديثًا بعد الحفظ للمستخدم المعني، مع استعادة التحديث بالاستعلام كل 3 ثوانٍ أثناء ظهور شاشة POS وعند العودة إليها.
إلغاء الصلاحية ينطبق أيضًا على المدير إذا كان له POS User صريح؛ الدور وحده لا يتجاوز الخانات.
عند غياب أي صلاحية مطلوبة، يلزم مدير آخر لديه صلاحيات العملية والهالك والفرع والبراند ونوع الطلب.

الاعتماد إما بباسورد `Fixed POS Approval Password` الموجود في POS User للمدير، أو OTP.
الباسورد هو حقل اعتماد POS الموجود سابقًا باسم `discount_approval_password` وليس باسورد تسجيل الدخول.
لطلب OTP، يختار الكاشير المدير وطريقة One-time code ثم Request one-time code.
يُولّد الكود عند طلب الكاشير ويصل مباشرة إلى جرس الإشعارات في حساب المدير المحدد، مع تفاصيل العملية. يظهر أيضًا رابط الإشعار في Approvals. الكود يظهر للمدير فقط، صالح 5 دقائق ويستخدم مرة واحدة.

في المرتجع يرتبط أيضًا بالكميات المرتجعة سابقًا، فلا يقبل بعد مرتجع جزئي آخر على نفس المصدر.

### توحيد إشعارات الأكواد: الخصم والفويد والمرتجع والمصروفات

كشف فحص محاولة المستخدم عدم وجود Approval Challenge لخصم أو Notification Log لكود خصم. اختيار المدير في مسار الخصم القديم كان يفتح إدخال OTP فقط؛ لم يكن هناك طلب إنشاء كود أو إرسال إشعار من الكاشير. أضيف endpoint `request_pos_discount_approval_code` وزر Send code to manager مع تأكيد وصول الطلب ومعرف سجل الموافقة أو رسالة فشل واضحة. يرسل تفاصيل الخصم المقترح من المسودة، بما فيها خصم فاتورة ضيف محدد، ولا يعيد الكود للكاشير. مسار إصدار كود الخصم من المدير يرسل الإشعار أيضًا.

أضيف اختيار المدير وزر إرسال في Authorize Pending Expense، مع endpoint `request_shift_expense_approval_code`. كود المصروف يظهر في جرس المدير ويظل صالحًا 3 دقائق. إصدار الكود يدويًا من Shift Expense يرسل إشعارًا كذلك. الفويد والمرتجع يظلان مربوطين بجرس الموافق المختار عبر مسارهما المشترك. تكرار الطلب للكود الساري لا يكرر إشعاراته.

نجح 193 اختبار باك إند و11 مجموعة اختبارات واجهة. نجحت 10 تحققات فعلية للخصم، تشمل وصول الكود لأحمد عبر get_notification_logs ثم التحقق منه واستهلاكه ومنع تكرار استعماله. نجحت 5 تحققات فعلية للمصروف، تشمل وصول الكود للجرس ثم استخدامه لتقديم Journal Entry. كل مستندات هذه التجارب تم التراجع عنها. تم ضبط ربط POS Profile في معاملة تجربة المصروف مؤقتًا ليطابق الشيفت المفتوح ثم التراجع عنه؛ إعداد المستخدم الموجود لم يتغير.

المتابعة: Approval Challenge لطلب/إصدار/استهلاك/صلاحية الكود، وNotification Log مع فلتر for_user للموافق وdocument_name لمعرف Approval Challenge. أكواد الخصم تحمل Action = POS Order Discount، والمصروف Post Shift Expense.

### تسريع Reload واسترجاع شاشة الدفع

كان الدخول برابط طلب ينفذ get_order ثم bootstrap/context ثم تحميل المنيو، وبعدها get_order_state وget_order ثم get_guest_checks وإعادة تحميل المنيو. أصبح الطلب المقروء من الرابط يُعاد استخدامه مباشرة، ولا ينفذ استعلام حالة منفصل. استرجاع الدفع ينتظر حالة الطلب والشيفت وطرق الدفع وتقسيم الضيوف الحالية، ثم يفتح الدفع فورًا؛ تحميل المنيو مرة واحدة في الخلفية ولا يمنع الدفع. واجهة بيع جديد لا تظهر أثناء استرجاع الطلب، وتظهر رسالة استرجاع قصيرة. فتح بيع جديد يبدأ تحميل المنيو بالتوازي مع بيانات السياق. لا تُجلب قائمة الترابيزات للتيك أواي. Bootstrap بلا فرع يعيد السياق الكامل للفرع المختار بدل استدعاء إضافي.

استعلام المنيو كان يحمل مستند Selling Product كاملًا وكل الجداول الفرعية لكل صنف. أصبح يجلب حقول العرض وثلاثة جداول فقط يحتاجها التسعير والإتاحة في مجموعات، ويستخدم نفس resolve_price والأسعار الحية من Item Price. لا يوجد كاش أسعار بين المستخدمين أو بعد تحديث الأسعار. نتائج المنيو متطابقة مع خط الأساس في 9 حالات (الفروع الثلاثة × أنواع الطلب الثلاثة). المتوسط المحلي لتحضير المنيو نزل من 548.1ms إلى 135.4ms، أي نحو 75%، وهذا قياس تنفيذ API محلي ولا يتضمن الشبكة أو تحميل Frappe Desk.

نجح اختبار واجهة جديد يمنع تعليق استرجاع الدفع حتى إذا لم ينته طلب المنيو، ويؤكد قراءة طلب واحدة وتحميل منيو واحد وبداية متوازية للبيع الجديد. نجحت تجربة Chromium الفعلية لعرض شاشة الدفع برقم الطلب والإجمالي بينما طلب المنيو لا يزال معلقًا. اختبارات الروابط والاسترجاع والشيفتات والصلاحيات والطلبات المقسمة استمرت في النجاح. الدليل: docs/verification/2026-11-05-pos-startup-performance.json.

### تبسيط البوب أب وسياسة إعادة إرسال OTP

حُذفت من عرض البوب أب: وقت الطلب، تاريخ انتهاء الصلاحية، رقم طلب الموافقة، أساس احتساب الخصم، الضريبة قبل وبعد، وإجمالي التخفيض شامل الضريبة والتقريب. تظل مبالغ قبل الخصم وقيمة الخصم والمطلوب تحصيله، وبيانات الطلب والأصناف والسبب والكود وعدّاد صلاحيته. راجع Chromium موافقات الخصم والفويد والمرتجع والمصروفات على الكمبيوتر والموبايل، مع التحقق من غياب الحقول المحذوفة وعدم الانتقال لصفحة أخرى.

رسالة الكاشير أصبحت «تم إرسال الكود للموافق» بدون رقم Approval Challenge. تشترك كل شاشات طلب الأكواد في ذاكرة إرسال محلية مرتبطة بالعملية والموافق: الرجوع من Fixed Password إلى OTP، أو إعادة اختيار نفس الموافق لنفس العملية، يعرض نفس حالة الكود ولا يستدعي API مجددًا. حتى الكود المنتهي لا يُعاد إرساله تلقائيًا؛ يلزم زر إعادة إرسال.

زر إعادة الإرسال يظهر مع انتظار 60 ثانية وعدّاد واضح. السيرفر يطبق نفس الحد؛ resend=1 خلال المهلة يعيد حالة الكود الموجود دون إشعار جديد، وبعد المهلة يصدر كودًا جديدًا ويبطل السابق. استدعاء عادي بدون resend يظل يعيد الكود الموجود دون إنشاء جديد. المعرّفات والتوقيتات ما زالت محفوظة في الباك أوفيس للمتابعة.

نجح 200 اختبار باك إند و13 مجموعة واجهة. اختبارات الواجهة أثبتت عدم إرسال طلب عند تبديل الطريقة، ومنع إعادة الإرسال قبل المهلة، وإرسال resend=1 فقط عند الطلب الصريح بعدها. معاملات فعلية اختبرت انتظار السيرفر وإلغاء الكود القديم وإرسال الجديد للخصم والفويد والمرتجع والمصروفات، مع نجاح استخدام الكود في الإلغاء والمرتجع وصرف المصروف وتراجع كل بيانات التحقق.
